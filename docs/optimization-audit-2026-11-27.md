# media-dedupe 多维优化探测

审查日期：2026-11-27（Asia/Shanghai）。基线：`cd72ee8`，工作区初始无未提交修改。重点参考结构统一提交 `46bc90e`、其后的打包修正，以及当前 `xwang-ui v0.6.0` 前端。以下是当前版本的改进项，不将所有问题归因于结构或 UI 迁移。

审查覆盖扫描、TXT 复核、SQLite 读写、结果浏览、删除、前端异步状态、打包和验证流程。本次只交付文档；复现所用文件都由临时目录生成，临时测试源码已经清理。

## 优先级与结论

P1 表示可能误删、遗漏结果或让失败操作看起来已经完成，应优先处理；P2 表示规模扩大或特定交互下的性能、可靠性和维护问题。“代码确认”不等同于测得了用户机器上的耗时。

| 编号 | 优先级 | 问题 | 证据状态 | 建议工作量 |
| --- | --- | --- | --- | --- |
| MD-01 | P1 | 删除没有完整绑定扫描快照与组成员，改写后的文件仍可被删 | 临时文件复现 | 中 |
| MD-02 | P1 | 部分删除失败被 UI 忽略，普通组可能提前标记已处理 | 代码确认 | 中 |
| MD-03 | P1 | 结果页只取 500 组，无翻页，排序也不是全量排序 | 代码确认 | 中 |
| MD-04 | P2 | 读列表/详情加载全库并逐组查询，每次开关数据库还执行迁移与 checkpoint | 代码确认；耗时待测 | 中 |
| MD-05 | P2 | TXT 全文复核恢复为组内全配对，缓存与内存预算不能消除平方开销 | 代码确认；规模收益待测 | 中到大 |
| MD-06 | P1 | 切换项目后旧详情和异步响应没有隔离，删除请求可能混用项目与文件 | 代码确认；UI 竞态待测 | 中 |
| MD-07 | P2 | 共享打包断言仍有 SIGPIPE 边界，发布工具与检查未完全固定 | Shell 机制复现、代码确认 | 小到中 |

建议顺序：先 MD-01/02/06 收紧删除与项目状态，再将 MD-03/04 作为同一批分页改造，随后处理 MD-05。MD-07 可以独立推进。

## MD-01：删除入口要验证成员身份和扫描后的文件变化

**依据**

- `go/internal/appapi/appapi.go:1048-1089`：`DeleteFiles` 接收调用方给出的 `Paths`；只有传入 `GroupIDs` 才调用组校验，之后直接进入文件操作。
- `go/internal/appapi/appapi.go:1186-1233`：`validateGroupDeletes` 验证所选组是否还留有文件，但不拒绝不存在的组，不验证每个路径确实属于该组，也不比较文件与扫描时的身份、大小、修改时间或摘要。
- `go/internal/appapi/appapi.go:1068-1078`：批量删除同样依赖之前缓存的 `cleanup_candidate`，删除前没有重新核对文件内容。

**影响和复现**

在临时项目中为 `keeper.txt`、`candidate.txt` 建立精确重复组，然后将候选文件改成不同长度的新内容。调用当前 `DeleteFiles` 后得到 `succeeded=1, failed=0`，新内容文件被删除。再传入不存在的组号 `999999` 和从未入库的 `unrelated.txt`，调用也成功删除了该临时文件。

这是本地绑定 API 的校验缺口，不表示存在公网删除接口。正常使用时，扫描和清理之间的外部编辑、路径替换，以及 MD-06 的项目切换都会使旧结果失效。回收站模式也会误移动文件；永久删除的后果更严重。

**解决方案**

1. 在共同删除入口由 `projectId + scanGeneration + groupId + fileId` 解析路径；拒绝未知组、未知成员和重复/矛盾选择，不把客户端路径当作授权依据。
2. 删除候选与保留文件都比较扫描快照：文件类型、身份、大小、纳秒修改时间；不一致则要求重扫。永久删除和高风险场景复核相应摘要；不能仅凭“还有一个路径存在”判断副本仍安全。
3. 将“用户手动选择待核对版本”和“批量清理已确认副本”作为显式操作类型，服务端沿用现有 `cleanup_candidate/review_required` 语义。
4. 对同一项目的扫描结果替换、推荐切换与删除执行建立互斥/代次校验。检查到执行仍有文件系统竞态，避免宣称一次 `Stat` 就能完全消除它。

**验收**：候选或保留文件被改写、路径被替换、未知组、跨项目 `fileId`、缺少组信息、同时重扫等情况下均不误删；正常重复清理和显式人工核对删除仍可用。所有场景只使用测试临时文件。

## MD-02：部分失败需要保留为可重试状态

**依据**

- `go/frontend/src/App.tsx:160-161`：单组和批量删除都只 `await api.DeleteFiles(...)`，未消费返回的 `failed`，随后关闭确认框、刷新并跳转。
- `go/internal/appapi/appapi.go:1089-1094,1179-1183`：逐文件失败存在返回 DTO 内，不一定表现为 Promise rejection。
- `go/internal/appapi/appapi.go:1130-1149`：普通组只要本次删掉过文件且剩余数量介于 1 和原数量之间，就可能标记 `processed`。例如三成员组删除两个候选，一成功、一失败，仍符合该条件。
- `go/internal/appapi/appapi.go:1096-1106,1131`：删除后的缓存打开、加载、操作记录错误有被忽略的路径。

**影响**：被占用文件、权限错误或断开的磁盘可能被用户理解为清理成功；组又从“待处理”页消失，失败文件难以继续处理。物理文件操作与 SQLite 不具备同一个事务，必须显式表达部分成功。

**解决方案**：统一返回成功、失败、取消及元数据更新失败四类结果；UI 展示失败路径和原因，只重试失败子集。组状态应按剩余的有效清理候选计算，仍有候选/失败时保留待处理或部分完成状态。文件操作前记录操作 ID 与意图，执行后更新结果；日志落盘失败时提示可重扫修复，不吞错。

**验收**：三文件组的一成功一失败场景不标记全部处理；失败项仍可见并能单独重试；重复点击不会重放已成功项；文件已经删除但数据库写入失败时给出明确恢复路径。

## MD-03：用服务端分页和全局排序替代固定 500 组

**依据**

- `go/frontend/src/App.tsx:147,160`：请求固定 `limit: 500, offset: 0`。
- `go/frontend/src/App.tsx:77-120`：结果页没有分页/继续加载入口；“全选”仅选中已返回集合。
- `go/frontend/src/App.tsx:83`：按空间、成员数、组号的排序在前端对子集进行。
- `go/internal/appapi/appapi.go:844-859`：后端先固定按置信度排序，再截断，未应用前端传来的排序选择。

**影响**：超过 500 组的结果不能完整浏览；最大可释放空间的组可能不在第一页，切换“按可释放空间”也找不到它。标题总量与可操作列表不一致。

**解决方案**：API 返回 `{items,total,nextCursor}` 或明确的页码信息；后端白名单解析排序，在筛选后、分页前统一排序并增加稳定的 `groupId` 次序。UI 提供分页或加载更多，区分“本页全选”和“全部匹配结果”。批量跨页操作传筛选快照/明确 ID 集合并由服务端复核，避免扫描代次变化后选错文件。

**验收**：使用 501、2,000 组固定数据验证每组均可达、无重无漏；最高空间组故意放在低置信度区仍可排到空间排序首页；筛选、翻页、批量选择和重扫后的选择失效规则一致。

## MD-04：缩小 SQLite 查询范围并管理连接生命周期

**依据**

- `go/internal/cache/cache.go:1061-1121`：`LoadReportGroups` 先查组，再查状态，随后逐组查询成员，形成约 `G + 2` 次 SQL；还会解析全量理由 JSON。
- `go/internal/appapi/appapi.go:752-859,896-912`：列表甚至单组详情都先调用全量加载；列表完成成员分类、封面处理之后才分页。
- `go/internal/appapi/appapi.go:692-699`、`go/internal/cache/cache.go:23-48`：每次 API 请求创建数据库句柄、执行 `init()`，关闭时强制 `wal_checkpoint(TRUNCATE)`。
- `go/internal/appapi/appapi.go:811-814` 生成封面，而当前结果表 `go/frontend/src/App.tsx:120` 没有使用封面字段。

**影响**：列表每次输入搜索词都可能触发全库工作；查看一个组也随着整个库增长。与后台扫描并行时，频繁 checkpoint 增加锁争用的可能。当前 `GetScanStatus` 直接读内存，不应误算成每 800 ms 都打开 SQLite。

**解决方案**：与 MD-03 一起增加列表聚合查询和按组详情查询，只载入当前页的必需字段；若仍需成员数据，按本页组 ID 一次批量查询。迁移在首次打开/版本变更时执行；按项目复用连接并管理关闭，checkpoint 放到扫描结束或空闲维护阶段。删除/移动项目时应先结束读写并释放句柄。移除当前列表不使用的封面准备工作。

**验收**：记录 100/1,000/10,000 组的 SQL 次数、冷/热列表及单组详情 p50/p95、查询分配量；单页查询次数应为常数级，详情不加载其他组。扫描并发浏览时无锁超时回归。此处没有预设“提升多少倍”。

## MD-05：全文复核需对配对数、读取和缓存写入共同设预算

**依据**

- `go/internal/textdedupe/matching.go:30-79` 先折叠相同摘要并生成候选；但 `go/internal/textdedupe/verify.go:31-35,80-119` 又对恢复后的关联组逐对复核。
- `go/internal/textdedupe/verify.go:44-78` 的 64 MiB 预算只限制保留的字符串。超预算文本会被当前配对完整读取，下次配对可能再次读取。
- `go/internal/textdedupe/content.go:18-26` 全文件读取、解码和规范化；构建无空白版本也会额外分配字符串。
- `go/internal/cache/cache.go:575-595` 每一对单独读缓存，未命中时单独执行写入；命中并不能减少配对遍历数。

**影响**：包含 1,000 个成员的关联组有 499,500 对，2,000 个成员有 1,999,000 对，这是代码中的精确配对数量，不是耗时基准。重复版本展开后会对相同摘要组合反复查缓存；大文本超预算时还会放大磁盘读取。

**解决方案**：先按摘要对去重并在一个复核批次内复用正/负结果，再使用有界事务批量写入缓存；保留候选关系，优先验证真正关联的摘要对，其他关系按需展开。大组显示“尚未复核/部分复核”，不能将未复核误当作不相似，更不能升级成可自动删除。内存预算应覆盖正在读取、解码及规范化的数据，并支持读取期间取消；需要时采用分块规范化/磁盘中间结果。

**验收**：固定同名但内容不同、相同摘要多副本、链式关联和单个超大 TXT 样本；记录唯一摘要对数、原始配对数、文件读取次数、缓存 SQL 次数、峰值 RSS、取消延迟。优化前后已验证的包含关系、字符位置和人工核对语义不变。

## MD-06：项目切换必须同时隔离详情、选择和异步请求

**依据**

- `go/frontend/src/App.tsx:145-157`：`currentId`、`groups`、`detail`、`selected` 独立存在；`refreshGroups`、`openGroup` 的异步结果没有项目/请求代次检查。
- `go/frontend/src/App.tsx:160`：删除用当前 `current.id`，路径和组号却取自保留的 `detail`。
- `go/frontend/src/App.tsx:164` 的项目选择更新 `currentId` 并切到配置页，但未同步清掉旧详情、选择和确认框，也未取消旧的详情请求。
- `go/frontend/src/App.tsx:27-28,153`：事件 hook 依赖回调，传入的内联刷新函数在每次渲染都会改变，造成反复退订/订阅。

**影响**：A 的 `openGroup` 请求未完成时切到 B，随后 A 的慢响应会写入旧详情并执行 `setView("group")`，重新打开属于 A 的详情；列表慢请求也可能覆盖新项目的结果。这与 MD-01 的路径校验缺口组合后，可能发生用 B 的项目 ID 删除 A 的文件。单纯切换项目会进入配置页，不能据此说旧详情始终留在屏幕上。这里未用桌面 UI 注入延迟实测竞态，结论来自状态与请求字段的直接数据流。

**解决方案**：以 `{projectId,scanGeneration}` 为详情/列表/选择/确认操作的共同身份；切换时同步清空旧页面状态，未加载完成时禁用操作。每次异步返回校验 request ID 和项目身份；删除确认框固定显示并提交创建确认时的快照，服务端再次核对。用稳定回调或 ref 承接事件，初始化信息与项目刷新拆开；搜索增加短防抖并丢弃旧响应。

**验收**：A 慢响应在 B 快响应之后返回、A 详情切到 B、确认框打开时切换/重扫、连续搜索时响应乱序；均只显示并操作当前有效快照，事件订阅数量不随进度渲染累积。

## MD-07：共享打包脚本仍需边界断言和可重复的发布验证

**依据与边界**

四仓的 `tools/common.sh`、`build.sh`、`build.ps1`、`package.sh`、`package.ps1` 和 `docs/packaging-contract.md` 已逐字比对一致。目录和标准包命名目前匹配，无需再次改名。

- `.github/workflows/release.yml:94-109` 仍使用 `echo "$names" | grep -q ...` 检查归档；在 `pipefail` 下，长名单早命中后写端会遭遇 SIGPIPE。
- `tools/package.sh:118,179` 的模板 B 分支同样有该写法；本项目是模板 A，因此不能把模板 B 的故障说成当前本项目正常打包必现。
- `tools/package.sh:83-100,135-152` 重复定义 `component_src`/`copy_component`，后者覆盖前者，后续容易只改到无效定义。
- `.github/workflows/release.yml:71-75` 安装 `wails@latest`，未固定到模块版本；setup-go 未设置迁移后 `go/go.sum` 的 cache-dependency-path；发布流水线未运行 Go 测试。

**已执行复现**：Bash `pipefail` 下，将 20,000 条归档路径装入变量后执行 `printf '%s\n' "$names" | grep -q '^VideoLib/tools/scraper/'`，匹配存在但返回 `141`。这确认的是共享写法的长输入问题，不是声称本项目当前小型 `.app` 归档已构建失败。

**解决方案**：用临时名单文件加 `grep -q pattern file` 或 here-string，避免向会提前退出的读端持续写管道；四仓同改并添加大名单边界验证。删除重复定义，用固定模板版本/摘要验证维持同步，项目差异继续留在配置和钩子。发布固定 Wails CLI 到 `go.mod` 对应版本，设置 Go 缓存路径，并在发布前运行现有 Go 测试与前端构建。

**验收**：正常和缺失入口两类名单分别返回成功/失败；长名单不受条目顺序影响；从干净 checkout 构建，检查解压布局、版本元数据与应用内更新资产匹配。Windows 和 macOS 包都要实际执行验证。

**跨仓同步：修法与实测边界已定稿（2026-11-27，grabber 仓已落地）**

grabber 仓已按同一份文件改完，可直接作为四仓模板：断言统一改成「先落名单 → here-string」，即先 `names="$(unzip -Z1 "$zip")"`，再 `grep -q "^${PRODUCT}/tools/" <<<"$names"`。here-string 不经过写端进程，`grep -q` 一命中就退出也不会再顶出 141。

- 复现边界（4000 条目归档、tools 条目排在最前、总量远超管道缓冲）：旧写法 `printf '%s\n' "$names" | grep -q …` 在匹配**存在**时返回 1，即漏检；新写法返回 0。触发条件是「shell 内建 echo/printf 往管道灌大变量 + 匹配在前」，随条目数增长放大。
- 另一条边界：由 `unzip -Z1` 直接产出、不经变量回灌的写法，本机未复现 141（unzip 自己承担了写端行为），但仍一并改成 here-string——判定结果不应取决于写端是谁、缓冲多大。
- 本仓实际位置：`.github/workflows/release.yml:96,99` 是 `echo "$names" | grep -q / -qx`，断言归档根有 `media-dedupe.app/Contents/MacOS/media-dedupe` 与 `media-dedupe.exe`；`tools/package.sh:118,179` 仍是 `printf '%s\n' … | grep -q`，属模板 B 分支，本仓不执行但要随四仓同步改掉。
- 本项目是模板 A，生效的是那两条「必须存在」的断言：命中在前被顶成 141 时走 `|| die` 一侧，表现为**误报失败、发版中断**，不是静默漏检。两个方向都要在验收里覆盖。
- 验收补充：除「长名单早/晚命中」外，各造一份 tools 在前、tools 在后的归档，确认漏检方向（本该 die 却静默通过）与误报方向（本该通过却 die）都不再出现。
