## 需要修正的细节

### MD-01：keeper 也能被删，且修复成本比「中」更低

`validateGroupDeletes`（`go/internal/appapi/appapi.go:1222-1231`）只统计「不在删除列表里、且仍存在的成员」，候选文件还在就满足 `alive >= 1`。因此把该组**推荐保留**文件的路径放进 `Paths` 同样能通过：组会反向变成「保留候选、清掉推荐文件」。原文只写了「改写后的文件被删」和「未入库路径」，没有覆盖这一条。

两点原文未提、但直接决定工作量：

- `DeleteRequestDTO.FileIDs` 在 `DeleteFiles` 里只被赋值（`:1077`）从未读取，服务端按 `fileId` 解析路径几乎零成本。
- `files` 表已存 `size_bytes / mtime_ns / inode / device / status`（`cache.go:55-66`），快照比对不需要新增存储或迁移。

严重度分层：回收站模式下误删可恢复，永久删除 + 原地覆盖才不可逆。同意 P1，但可以先做「按 fileId 解析 + 归属校验 + 快照比对」，不动前端。

### MD-02：失败记录只写不读

`delete_ops` 全仓只有 `INSERT`（`cache.go:986`），没有任何 `SELECT`，也没有暴露给前端的接口。因此「失败项可单独重试」不是前端加提示就能完成，必须先补读取面。前端删除后的跳转（`pending.find(g => g.groupId !== doneId)` 后再 `openGroup`）会让失败文件在界面上彻底消失。

### MD-04：成本被低估

点一次「忽略」触发 **3 次全量加载**：`SetGroupStatus` → `refreshLastSummary`（自身又开缓存做全量 `LoadReportGroups`），前端随后 `refreshGroups` 再来一次，外加 `refresh` 里的 `ListProjects`。每次打开都要执行 `init()`（3 条 CREATE + 约 8 条注定失败的 ALTER + 一次 `pragma_table_info`），关闭时 `wal_checkpoint(TRUNCATE)`。

封面确实是死代码：`coverThumbUrl` 只在 `api.ts` 的 mock 里出现，`App.tsx` 无引用。

### MD-05：平方开销不止 verify 一处

原文只点了 `verify.go` 的两两配对，但 `matching.go:100-149` 同样对组内代表两两汇总 Confidence、并为每个成员拼接 O(k) 条 `fmt.Sprintf` 证据串，也是 O(k²)，且直接写进 `reasons_json`。只优化 verify 一段，matching 段的平方开销仍在。

另一个放大器：verify 的缓存错误走 `hooks.fatal`（`pipeline.go:388` → `:350-353`），**一次缓存读写失败会取消整次扫描**；配对次数越多，踩中概率越大。

### MD-06：触发路径改写

不是「删除用当前 `current.id`、路径取自保留的 `detail`」——`deleteSelected` 的 `action` 闭包捕获的是打开确认框那次渲染的值，两者同源。真正的问题是**同一次渲染里 `current` 与 `detail` 本来就可能属于不同项目**：A 的 `openGroup` 慢响应在切到 B 之后才执行 `setDetail(A)` + `setView("group")`。

补充一条原文未提的：确认框状态独立于项目切换，切换后不会关闭，此时点「确认」仍按 A 的快照执行——这是最危险的一条路径。

### MD-07：本仓真正生效的只有三条

- `release.yml:96/99` 的 `echo | grep -q` 属实，但本仓归档条目只有几条（`.app` 内部 3-5 条、Windows 1 条），远小于管道缓冲，当前几乎不可能触发。原文对此的边界声明是准确的，不必再降级。
- `package.sh:118` 因 `tools/config.env:19` 的 `HAS_PYTHON=0` 走不到；`:179` 只在 `--full` 且模板 B 下执行。与原文措辞一致。
- `component_src` / `copy_component` 重复定义属实；`grabber` 仓同样是两份，属共享模板问题。
- `wails@latest` 属实：`go/go.mod` 是 `v2.16.0`。
- **setup-go 缓存比原文说的更严重**：`actions/setup-go` 的 `findDependencyFile` 只在 `GITHUB_WORKSPACE` 根目录找 `go.sum`，本仓在 `go/` 下，`restoreCache` 抛错后被 `main.ts` catch 成 `core.warning`，结果是**模块缓存静默失效、每次都全量下载**，而不是构建失败。这是 `46bc90e` 目录重构的副作用。
- 未跑 `go test` 属实：全仓只有 `release.yml` 一个 workflow，`tools/build.sh` 也不跑测试。

## 修订后的执行顺序

1. **发版可信度（MD-07 子集）**：`setup-go` 补 `cache-dependency-path: go/go.sum`；Wails CLI 固定到 `go.mod` 的版本；发版前跑 `go test ./...`。改动小、无产品行为变化，先落地。
2. **MD-01 服务端半边**：按 `projectId + groupId + fileId` 解析路径、拒绝未知组/非成员/keeper、删除前比对大小与纳秒 mtime（必要时 inode/device）。不动前端，先堵住误删面。
3. **MD-02 + MD-06 同批**：两者都要「项目 + 扫描代次」身份，一起做避免改两遍；为 MD-02 补 `delete_ops` 的读取面与部分失败 UI。
4. **MD-04 先于 MD-03**：先裁查询（单组详情单条 SQL、列表聚合、去封面、连接复用），再叠分页（本轮用 offset + total，不用游标）；否则分页接口会建在 N+1 之上返工。
5. **MD-05 最后**：先止血（组内配对上限定、大组标「未完全复核」、缓存错误不 fatal），再谈摘要对去重与批量事务写缓存。

与原文档顺序的差异只有一处：把 MD-04 提到 MD-03 之前（原文档为同批并行），以及把 MD-07 的三条提前到第一步。

## 本轮已完成

- 第 1 步：`release.yml` 固定 Wails 版本（取自 `go.mod`）、补 `cache-dependency-path: go/go.sum`、发版前执行 `go test ./...`。
- 第 2 步：`DeleteFiles` 改为服务端解析删除目标。新增 `resolveDeleteTargets` / `selectDeleteTargets` / `checkGroupInvariants` / `checkDeleteSnapshot`，`cache.LoadFileSnapshot` 提供扫描快照；`validateGroupDeletes` 的分组不变量并入上述流程。新增 `delete_preconditions_test.go`（10 个用例：改写候选、替换路径、非成员路径、未知组、keeper、缺组信息、mtime 变动、路径解析、批量候选、文件已消失）。
- 第 3 步：MD-02 + MD-06。
  - 服务端：`DeleteResultDTO.Failed` 带上 `fileId/groupId`（重试只需提交失败子集）；新增 `MetadataErrors` 收集结果库更新失败；组状态改按「还剩多少可删候选」判定，部分失败不再把组标成已处理；成功删除的 `files` 行在**所有**组里统一清理并跑一次 `PruneReportGroups`，列表不再显示已删掉的候选；`refreshLastSummary` 返回错误，删除路径把它并入 `MetadataErrors`，`SetGroupStatus`/`SetRecommended` 的汇总刷新失败改为写应用日志（状态本身已落库，属降级）。
  - 前端：项目切换由 `setProject` 统一清空详情/选择/确认框/状态；列表与详情请求带「项目身份 + 请求代次」校验，慢响应不会覆盖当前页面；搜索从每次按键一次全量查询改为 200ms 防抖；事件回调换成稳定引用，不再每次渲染退订重订；删除统一走 `runDelete`，按返回的 `failed` 弹出失败清单并提供「重试失败项」，重试只提交失败的 `fileId`，成功项不会重放。
- 第 4 步：MD-04 查询裁剪。
  - 列表：`cache.LoadGroupSummaries` 一条聚合 SQL 完成筛选、排序、分页；排序在 SQL 层按白名单（confidence/size/members/id）解析，并补 `g.id` 稳定次序。`GroupListDTO` 去掉从未被前端读取的 `coverThumbUrl`，列表不再生成封面、不再申请缩略图根目录。
  - 详情：`cache.LoadGroup` 两条查询（组 + 成员），不再为了一个组加载整库。
  - 汇总：`cache.LoadGroupTotals` 一条聚合 SQL 代替「全量加载 + ComputeSummary」，扫描结束与状态变更都走它。
  - 删除：`resolveDeleteTargets` 与 `applyDeleteBookkeeping` 改成按组号 `LoadGroup`，删除 N 组从 G+2 次查询降到 2N 次。
  - 连接生命周期：`init()` 用 `PRAGMA user_version` 做版本门控（`schemaVersion = 3`），命中版本时迁移一条语句都不执行；`Close()` 不再强制 `wal_checkpoint(TRUNCATE)`，改成显式 `Checkpoint()`，只在扫描结束与删除记录写入后调用。
  - 索引：补 `idx_items_group ON duplicate_items(group_id)`。此前 `duplicate_items` 只有外键没有索引，按组取成员和聚合都要扫全表。
  - 基准（5000 组 × 3 成员，M1 Pro，`internal/cache/query_bench_test.go`）：列表 **3.60s → 21.9ms**，单组详情 **3.60s → 0.65ms**；列表 SQL 从 G+2 条降到 1 条，详情从 G+2 条降到 2 条。这是查询层的耗时，不含 DTO 映射与前端渲染，且只在本机测过。
- 第 5 步：MD-03 分页。
  - `cache.CountGroupSummaries` 与分页查询共用同一个 `GroupQuery.where()`，所以 `total` 恒等于「当前筛选下的全部匹配组数」，不会随已加载页数漂移。
  - `ListGroups` 返回 `GroupPageDTO{items,total,limit,offset,hasMore}`；`limit<=0` 取默认 100，上限 500 由服务端夹紧，客户端不再能要求「全给我」。
  - 前端每页 100 行，「加载更多」按 offset 追加并按 `groupId` 去重；页脚恒显示「已显示 N / 共 M 组匹配」，未载完时补一句「勾选与批量删除只作用于已加载的行」。
  - 「全选」改称「全选本页」，语义与实现一致：批量删除只处理已加载且被勾选的行。
  - 追加页与首页共用同一个请求代次，切换项目/筛选时旧页直接丢弃，不会把两套筛选结果拼在一起。
  - 新增 `TestListGroupsPagesBeyondTheOldCap`（620 组：默认首页 100 行且 `hasMore`、第 7 页能取到第 620 组、`limit=5000` 被夹到 500、`offset` 越界返回空页而非报错）。
- 第 6 步：MD-05 平方开销与 fatal 降级。
  - `verify.go`：每组全文复核封顶 `maxVerifyPairsPerGroup = 400` 对；超出时循环在达到上限后停止，并给组内**每个**成员追加一条「组内共 N 个成员，仅复核了前 400 对全文，其余组合未复核，判断前请抽查」——静默截断会被读成「已复核、未发现包含关系」，必须显式说明。
  - `verify.go`：复核缓存（读写）失败不再中断整个复核阶段。记一次 `text_cache` 错误后停用缓存、在内存里把剩下的对算完，证据照常写入。此前一次 `SQLITE_BUSY` 会让后续所有组失去证据。
  - `matching.go`：每个成员的成对证据封顶 `maxEvidencePerMember = 8` 条，其余汇总成一行「组内另有 N 条…未逐条列出」。此前 500 个版本的组会给每个成员的 `reasons_json` 写 500 条近似字符串。
  - `pipeline`：TXT 阶段错误分类抽成 `recordTextFailure`。`text_cache` 只有在 `isFatalIOError` 成立（磁盘级故障）时才 fatal，否则降级为 `aux` 警告；`text_decode` 仍是逐文件跳过。此前缓存里任何一次读写失败都会取消整次扫描。
  - 新增 `verification_limits_test.go`（30 成员组触发 400 对上限并检查每个成员都有说明；坏缓存下只报一次错、证据仍生成；12 个近似版本的组成对证据条数受限）、`TestRecordTextFailureClassifiesCacheErrors`（缓存锁 → 警告，`EIO` → fatal，解码错 → 逐文件）。
- 验证：`go vet ./...` 干净、`go test ./...` 全绿（appapi 新增 15 个用例、cache 新增 4 个、textdedupe 新增 3 个、pipeline 新增 1 个）；`npm run build`（tsc + vite）通过；mock 预览下实际走通「建项目 → 结果列表 → 批量删除 → 部分失败弹窗 → 重试」，并单独把页大小临时改为 2 验证「全选本页 → 已勾选 → 加载更多 → 全部载入 → 删除后回到空列表」，验证后已还原为 100。


### 第 2 步的行为变化（需要知悉）

1. 请求必须带 `projectId` 与 `groupIds`，否则直接拒绝；路径不再是授权依据，只在组内用于指名成员。
2. 删除组内推荐保留文件会被拒绝（此前仅前端禁用勾选）。
3. 候选文件的大小或纳秒 mtime 与扫描记录不一致时，**只跳过这一个文件**并给出原因，同批其它文件照常删除、该组留在「待处理」；文件已不存在同样按逐文件失败上报。（最初实现为整批拒绝，200 组里 1 个文件被改就整批不动，已在「遗留风险处理」里改为逐文件。）
4. 文件身份（inode/device）只在双方都记录过时比对，Windows 与旧缓存跳过。
5. 检查与删除之间仍有文件系统竞态（原文档已声明），一次 `Stat` 不能消除它。

### 第 3 步的行为变化（需要知悉）

1. 删除后组是否变成「已处理」按剩余清理候选判断：只要有候选没删掉，组留在「待处理」并显示剩余候选数。
2. 成功删除的成员立刻从结果里消失（此前非文本组要等下一次扫描才更新成员数与可释放空间）。
3. 部分失败会弹出失败清单，重试只提交这些 `fileId`；批量删除的重试同样按 `groupId + fileId` 定位。
4. 结果库更新失败不再吞掉：文件已删但库里没改的情况会在同一个弹窗里提示「需要重新扫描」。
5. 切换项目会关闭未确认的删除对话框、清空详情与勾选；异步响应带项目身份校验，旧项目的慢响应直接丢弃。
6. 重试时若某个组已被重新扫描或另一次删除清掉，它只作为一条失败上报（提示无需再删），同一批里还存在其它组照常执行，不再让整次重试报错；重试带来的 `fileId` 若无法落到任何已命名组，也按一条「不参与重试」的失败上报，不删任何东西。

### 第 4 步的行为变化（需要知悉）

1. 列表排序改由服务端对**全部匹配结果**排序后再取页；此前是「先按置信度截断 500 条，再在前端对子集排序」。同一份数据下，按可释放空间排序现在能看到真正的第一名。
2. 删除各处的「可释放空间」不再把推荐保留文件算进去（与清理候选定义一致）；此前 `ComputeSummary` 只按 action 判断，推荐文件若被标成候选会被计入。
3. 项目表头（组数/可释放）与列表来自同一套聚合，不再需要整库加载。
4. `coverThumbUrl` 从接口移除（前端从未使用），列表不再为每组生成封面。
5. `wal_checkpoint` 只在扫描结束与删除记录写入后执行，读请求不再持锁做 TRUNCATE；WAL 由 SQLite 自动 checkpoint（默认 ~1000 页）兜底，关闭句柄时若 `-wal` 已超过 8 MB 再 TRUNCATE 一次，避免长期只读留下几 MB 垃圾文件。
6. 打开缓存时若 `user_version` 已是最新则跳过迁移；从旧版本升级（`user_version = 0`）仍会完整迁移一次。

### 第 6 步的行为变化（需要知悉）

1. 组内成员超过 29 个（严格说是配对数超过 400）时，只复核前 400 对；每个成员的证据里都会写明「其余组合未复核」。判定依据仍然是缓存指纹与已复核的对，不会因为限制而把组降级成「无证据」。
2. 复核缓存的错误从「取消扫描」变成「一条警告 + 本次不落缓存」。代价是下次扫描可能重新比对相同的一批文件；收益是几十分钟的扫描不会因为一次锁竞争而前功尽弃。
3. 每个文件的成对证据最多 8 条，多出来的汇总成一行计数。报告里的「为什么判定重复」仍然完整（指纹、覆盖区间、书名差异并未截断，截断的只是「和各成员的关系」条目）。

### 已知未做

- `delete_ops` 仍只有写入没有读取接口：失败项在当次会话内可重试，跨会话的历史失败记录还查不出来。需要时再加 `ListDeleteFailures` 与入口。
- 没有新增「部分完成」状态值，仍用 `pending` + 失败清单表达，避免影响报告与筛选口径。
- 删除不并发执行，因此原文档提到的「取消」类别暂不适用。
- 分页是 offset 型，没有用游标。删除后按「已加载行数」重载，位置基本不跳，但不是严格保位（前面的行被删掉时会整体上移）。要严格保位再换键集（keyset）分页。
- 没有「全选全部匹配」：批量删除只认已加载的行。要支持跨页全选，需要新增「按筛选条件删除」的接口与二次确认，风险面比现在大，本轮不做。
- 连接仍按请求打开，只是不再做迁移与 checkpoint；没有做按项目复用连接池。
- 一次页请求是「查页 + 查总数」两条 SQL（计数不复用页查询的窗口值），在 5000 组量级上两者都是毫秒级，未做合并。

### 第 5 步的行为变化（需要知悉）

1. 结果列表一次最多显示 100 行，其余靠「加载更多」追加；此前是固定 500 行且 501 组以后完全看不到。
2. 页脚一直显示「已显示 N / 共 M 组匹配」，「全选」按钮改名为「全选本页」，避免把「已勾选」误当成「全部匹配」。
3. `ListGroups` 的返回值从数组变成 `{items,total,limit,offset,hasMore}`，这是不兼容变更；仓库内调用点已全部更新，外部若有脚本直接调这个绑定方法需要跟着改。
4. `limit` 超过 500 会被服务端夹到 500，`limit<=0` 取 100——传 0 不再等于「取全部」。
5. 删除/忽略后的刷新会重新加载「当前已加载的行数」（上限 500），不再直接回到第一页；改变筛选或排序才重置到第一页。

## 遗留风险的处理（第 1–6 步执行后统一清账）

| 风险 | 处理 |
|---|---|
| 快照不符导致整批拒绝（第 2 步） | 改为逐文件跳过：该文件留在原处并作为一条失败上报，同批其它文件照删，组因仍有候选而留在「待处理」。 |
| 重试时组已不在结果中会让整次重试报错（第 3 步） | 改为按组上报失败（`GroupID` 有值、`FileID` 为 0，不参与重试提交），其余组照常执行；同一请求里落不到任何组的 `fileId` 同样按条上报而不是中断整批。 |
| 长期只读留下几 MB `-wal`（第 4 步） | `Close()` 时若 `-wal` 超过 8 MB 才 TRUNCATE 一次；正常情况仍依赖 SQLite 自动 checkpoint。 |
| 删除后列表跳回第一页（第 5 步） | 刷新时按「已加载行数」重载（上限 500）；只有筛选/排序变化才回到第一页。 |
| `ListGroups` 返回值不兼容（第 5 步） | 保留新结构。仓库内调用点全部更新；这是绑定层对外契约，若外部脚本直接调用需同步改。 |
| 每次请求开一次连接（第 4 步） | 暂不做连接池。真正的成本已由版本门控与去掉 checkpoint 消除，剩下的是 `sql.Open` + 一次 `ping`。 |
| `docs/` 两份审计文档未提交 | 仍保持未提交，等你自己 review 后按你的提交规范处理。 |

**按设计保留、不算缺陷的三点**（当时列为「待确认」，结论是维持现状）：

1. **推荐保留文件不能直接删**：要换保留对象先点「设为推荐保留」。这条比原设计更严，但它是唯一能防止「把要留的那份删掉、留下改名副本」的硬约束。
2. **部分候选已删的组仍留在「待处理」**：组只有在没有剩余候选时才自动转为「已处理」。
3. **成功删除的成员立刻从列表消失**：成员数与可释放空间即时下降，不再等下一次扫描。
4. **可释放空间不含推荐保留文件**：表头、列表、清理候选三处口径统一。

**没有做的一项**：跨页「全选全部匹配」。它需要新增「按筛选条件删除」的接口（服务端自行展开候选、二次确认、失败逐条回报），风险面比现在这套「只删已加载且被勾选的行」大得多；当前分页已保证 501 组以后可达，先用「加载更多 + 全选本页」覆盖日常场景。
